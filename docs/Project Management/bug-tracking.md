## Proposed bug workflow

> [!NOTE]
> This workflow is proposed for team confirmation; the export does not establish it as adopted policy.

1. **Report:** record reproducible steps, expected/actual result, environment/build, role/team context, screenshots/logs without secrets, and related feature card.
2. **Triage:** reproduce, separate bug from enhancement/documentation, assign impact and urgency, record owner, and choose target sprint/list.
3. **Fix:** link the branch/PR using the repository naming convention and add a regression test at the lowest effective layer.
4. **Review:** record code review, security/team-isolation impact, migration impact and exact checks run.
5. **Retest:** repeat the original steps on the identified revision and record result/artifact. Reopen or return the card if it fails.
6. **Close/archive:** only after the team’s Definition of Done is met; retain links to the fix and retest evidence.

## Proposed severity scale

| Severity | Proposed meaning |
| --- | --- |
| Critical | Data exposure/loss, authentication bypass, or core service unavailable with no workaround. |
| High | Core match/team workflow blocked or materially incorrect; limited workaround. |
| Medium | Significant defect with a practical workaround or limited scope. |
| Low | Cosmetic, wording or minor usability issue that does not corrupt results or block a workflow. |

Severity is separate from delivery priority. No severity labels were named in the exported board, so this scale must not be retroactively assigned as fact.
